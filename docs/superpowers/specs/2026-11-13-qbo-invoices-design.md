# chapi × QuickBooks Online 发票：按表建发票、停在发送前

状态：草稿，待用户批准（2026-11-13）

## 1. 目的和原因

用户给 chapi 一张表（Google 表格或 Excel），chapi 按表在 QuickBooks Online（下称 QBO）里逐张**建立并保存**发票，停在"已保存、未发送"的状态。用户在 QBO 里检查后自己点发送。

用户不想在 Intuit 开发者平台建应用（官方 API 的授权不分细项，一授权就能读写全账本），选了"浏览器登录网页版"的路线。用户的核心要求是：发送、删除、作废等高风险操作必须**硬拦截**，不能只靠提示词约束模型。

## 2. 目标 / 非目标 / 反目标

**目标**
- 按表批量建发票，客户不存在时可以新建客户。
- 开始写入前，先把核对结果（客户匹配、疑似重复发票、缺失的产品）交给用户确认。
- 完成后给出汇总：每行对应的发票号、金额、QBO 链接、成功还是失败。
- 允许修改 chapi 自己建的、未发送、未收款的发票（改错用）。

**非目标**
- 发送发票、发送提醒、收款、退款、贷项通知单、对账。
- 新建或修改产品/服务项目（产品不存在 → 标出来交给用户处理）。
- 支持官方 API。

**反目标（出现即视为失败，即使"功能上能用"）**
- 任何一张发票被发出去（邮件、短信、付款链接），或任何发票、客户被删除或作废。
- 修改了已有客户的任何字段。
- 修改了不是 chapi 建的发票，或已发送、已收款的发票。
- 模型能绕过拦截：自己连上 QBO 浏览器、拿到登录 cookie 直接发请求、改白名单等。
- 静默建出重复的客户或重复的发票。

## 3. 约束（基于现有代码）

- 模型现在通过 `chapi_browser.py` 用 CDP 连 cloakbrowser（`127.0.0.1:9222`，见 [supervisor.ts](../../../apps/server/src/supervisor.ts)、[options.ts](../../../apps/server/src/engine/options.ts) 的 `CHAPI_CDP_ENDPOINT`）。本机任何进程，包括模型的 Bash，都能连上本机的 TCP 调试端口。**所以 QBO 不能放进 cloakbrowser，也不能开任何 TCP 调试端口。**
- 模型和 chapi 服务端是同一个 Windows 用户在运行，理论上能读到浏览器配置目录里加密的 cookie。这是已知的剩余风险（见 §7）。
- 服务端 Node 依赖里目前只有 `chrome-remote-interface`，没有 playwright。chapi 运行时执行 `pnpm add` 会让 tsx watch 崩溃，需要 `touch src/index.ts` 恢复。
- 现有可复用的部分：`createSdkMcpServer` 进程内工具（[chapiTools.ts](../../../apps/server/src/engine/tools/chapiTools.ts)）、HITL 卡片（`ask_user` / `request_approval`，[hitl.ts](../../../apps/server/src/engine/hitl.ts)）、权限回调（[permissions.ts](../../../apps/server/src/engine/permissions.ts)）、加密密钥库（[secrets.ts](../../../apps/server/src/secrets.ts)）、实时画面（[browserView.ts](../../../apps/server/src/engine/browserView.ts)，CDP screencast）。

## 4. 考虑过的做法

在"浏览器登录"这条路线下比较了三种：

| 做法 | 说明 | 取舍 |
|---|---|---|
| **A. 独立浏览器 + 调用网页内部接口（已选）** | 服务端用 pipe 启动一个只登录 QBO 的浏览器；工具在已登录的页面里调用 QBO 网页自己的保存接口；网络层白名单默认拒绝 | 快、结构化、能拦死；要先录一次内部接口，QBO 改版后可能要重录 |
| B. 独立浏览器 + 模拟点击填表 | 隔离和拦截同 A，但工具模拟人填写表单 | 慢，界面改版就容易出错，下拉框等控件最容易失败 |
| C. 共用 cloakbrowser，模型直接操作，加拦截代理 | 改动最小 | 模型能绕过，不满足"硬拦截" |

用户选了 **A**。

## 5. 设计

### 5.1 QBO 专用浏览器（隔离）
- 服务端用 playwright-core 以 **pipe 方式**（`launchPersistentContext`，不开 `--remote-debugging-port`）启动，使用独立配置目录（如 `.qbo-browser-profile/`，与 `.browser-profile/` 分开）。只有服务端进程持有这个连接。
- 平时不开窗口（headless）。登录或重新登录时开窗口（headed），由用户本人在窗口里登录并完成两步验证。登录状态保存在独立配置目录中。
- 不把 QBO 的 cookie、配置目录路径、内部接口写进模型能看到的地方（工具返回值、日志、系统提示）。

### 5.2 网络层白名单（拒绝优先）
在专用浏览器的 context 上拦截**所有**请求，规则按顺序判断：
1. 读请求（GET/HEAD/OPTIONS）→ 放行。
2. QBO 网页用 POST 做查询的接口（例如 GraphQL 查询），按录到的**操作名称白名单**放行。
3. 写请求只放行以下三类，而且要检查请求体：
   - **新建发票**：请求体里不能带已有发票 Id，不能带"发送/待发送"类标记。
   - **新建客户**：请求体里不能带已有客户 Id（必须是新建，不能更新）。
   - **修改发票**：目标 Id 必须在 chapi 本地记录的"由 chapi 新建"清单里，而且工具在发请求前刚确认过该发票未发送、未收款；请求体不能带发送标记。
4. 登录模式下额外放行 Intuit 登录域的请求。
5. **其余一律拒绝**，并写入审计日志。QBO 改版后多出来的新写接口会被拒，只会导致功能失败，不会被意外放行。

录接口（我的决定）：先在 QBO 官方的公开示例公司（Test Drive，免登录、定期重置）里录新建发票、新建客户、修改发票的请求，据此写白名单和调用代码，不在正式账本里留下测试数据。之后用用户第一批真实发票在正式公司里验证一遍。如果 Test Drive 的接口和正式公司不一致或无法使用，再改为在正式公司里随用户第一批真实发票录制，不建测试单据。录制**不包括**点发送或删除，这两个操作靠默认拒绝挡住，不需要录。

### 5.2.1 锁定公司（我的决定）
首次登录时，由用户在确认卡片里确认要写入的公司，服务端记录该公司 ID（realmId）。网络层只放行发往这个 realmId 的写请求。每个批次记录 realmId，提交前再核对一次当前公司；不一致就拒绝写入，并提示用户。

### 5.3 给模型的工具（进程内 MCP，`mcp__chapi__qbo_*`）
- `qbo_status`：是否已登录、当前公司名。未登录时提示用户在 chapi 里点"登录 QuickBooks"。
- `qbo_lookup`：只读，按名称查客户、产品，按条件查已有发票（防止重复建）。
- `qbo_prepare_batch`：传入从表中解析出的结构化行，服务端逐行核对：
  - 客户：名称完全一致的直接使用；相近的（例如 "ABC LLC" 和 "ABC, LLC"）标为"疑似，需要确认"；找不到的标为"将新建"。
  - 客户特殊情况（我的决定）：
    - 名称一致但客户已停用：标为"停用，跳过"，请用户手动重新启用后再跑。重新启用属于修改已有客户，不开放。
    - 子客户：按完整名称（"上级:子级"）匹配。表里只写了子级名称、且恰好对应一个子客户的，标为"疑似"，由用户确认。
    - 与供应商或员工重名（QBO 要求这几类名称不能重复）：标为"重名，跳过"。
  - 新建客户的字段（我的决定）：名称，加上表里有的邮箱、账单地址；具体字段等样表定。
  - 产品：找不到的标为"缺失，跳过"。
  - 重复：同一客户、同一日期、同一金额的已有发票，标为"疑似重复"。

  返回一个批次 ID 和核对清单。
- `qbo_commit_batch(batchId)`：**由服务端自己**弹出确认卡片（复用 HITL），把核对清单展示给用户，用户逐项处理"疑似"项并确认后才开始写入，不依赖模型去调用 `request_approval`。之后逐行新建客户（如需）→ 新建发票，失败的行不影响其他行。返回汇总。
- `qbo_update_invoice(invoiceId, changes)`：只允许修改本地"由 chapi 新建"清单里的发票。执行前重新读取该发票，确认未发送、未收款，同样要经过服务端确认卡片。

不提供任何发送、删除、作废、收款工具。[permissions.ts](../../../apps/server/src/engine/permissions.ts) 里再加一层兜底：`mcp__chapi__qbo_*` 中名称含 send/delete/void/payment 等词的一律拒绝，写法参照 `looksLikeGmailSend`。

### 5.4 本地记录
- Prisma 新表，记录批次、行、新建的发票 Id 和发票号、新建的客户 Id、状态。"由 chapi 新建"清单以这张表为准。
- 审计日志：每个写请求（放行或拒绝）的时间、类型、目标 Id、请求体摘要。

### 5.5 前端
- 设置页或浏览器面板加"登录 QuickBooks"按钮：开窗口，显示登录状态（已登录 / 过期）。
- 确认卡片里用表格展示核对清单，并提供"疑似"项的选择（用已有客户 / 新建）。

### 5.6 数据来源与发票字段（用户 2026-11-13 提供）
- 源表：UP Property Leasing（`1-rW2nezaKDS0iiwEUIZmM_MzW9Ivsb-tBUxKdnO2t9I`），Lease Tracker 是租约明细。
- 每半个月（1–15 日、16 日–月底），chapi 按现有流程把源表数据算进收款表 Chapi - UP Landlord Commission Billing（`14HbVv335flb4I_Lb8iYa8J-3abOHaj9VIijOO8tfWnY`）的本期页签（例如「10/16-10/31/2026」）。页签下方按楼列出发票区块，三列：Product/service | Description | Amount，Amount 为纯数字。这一步沿用现有做法，规则见用户的 Unitpulse_Billing_Prompt.md，本设计不改。
- 本设计新增的一步：读取本期页签的发票区块，**一个区块对应一张 QBO 发票**，交给 `qbo_prepare_batch`。
- 发票字段：
  - 客户：每个区块对应的开票对象。QBO 现有客户命名为「业主-楼名」，例如 "Janet Chan-Solare"、"Harbor Group-Nari"、"David Chun-2600 S Catalina"。
    - 我的决定：第一次匹配后，用户在确认卡片里确认"区块名 → QBO 客户"的对应关系，服务端把它存成对照表，下次直接用，不再猜。
  - 发票号：现在用 UP-LE-xxx（租赁）和 UP-MK-xxx（营销）两个前缀，**数字部分共用一个递增序列**（例如 186、187、188 是 LE，193、194 是 MK）。
    - 我的决定：取 QBO 里 UP-LE / UP-MK 现有最大编号 +1 依次分配，在确认卡片里展示，用户可以改。
  - 发票明细行：Product/service 只用 `Leasing Service` 或 `Marketing Service`；Description 原样照搬；只填金额，不填 Qty 和 Rate；区块里的 Total 行不作为明细行写入，只用来核对发票合计。
  - 发票日期（我的决定）：默认为建立当天，在确认卡片里可以改。
  - 付款条件（我的决定）：优先用 QBO 里该客户的默认付款条件。客户没有设置的，按规则文件处理：Tripalink 各主体 Net 15，其余 Net 30。
- 防重复：同一客户的已有发票中，Description 里已经出现同一住户 + 同一房号的，标为"疑似重复"。
- 非目标：建好发票后回写 Bill & AR Tracker 或 Lease Tracker（现有做法是用户明确要求时才回写，保持不变）。

## 6. 由用户决定的部分
- 路线：浏览器登录网页版，做法 A。
- 允许新建客户；不允许修改或删除已有客户。
- 必须停在发送前；发送、删除、作废一律拦死。

## 7. 剩余风险（需告知用户）
- 模型能以同一 Windows 用户读取 QBO 浏览器配置目录，理论上可以解出 cookie 自己发请求。缓解办法：让 QBO 管理员给 chapi 专用浏览器开一个权限受限的 QBO 用户（可选，用户决定）。
- QBO 自身的自动提醒、自动发送设置不经过 chapi，需要用户在 QBO 设置里确认已关闭。
- 网页内部接口没有公开文档，QBO 改版会导致功能失败（拦截规则是拒绝优先，失败也不会放行）。
- 自动化操作网页版可能不符合 Intuit 使用条款，有被风控的风险。

## 8. 留给实现者决定
- playwright-core 启动的是 cloakbrowser 的内核还是普通 Chromium（如果 QBO 有反自动化检测，优先用 cloakbrowser 内核的可执行文件）。
- 登录窗口用系统窗口还是接入 chapi 实时画面。
- 具体的内部接口和 GraphQL 操作名称（录制后确定）。
- 发票区块由模型从收款表本期页签读出，交给 `qbo_prepare_batch` 的结构为：客户、发票号、日期、付款条件、明细行（产品、描述、金额）；实现时要先读一遍最近一期页签，确认实际格式。
